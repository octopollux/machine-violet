# Co-DM pilot — 2026-10-05

This records a staged, isolated prototype evaluation. After reviewing the latency results, the project owner **selected the co-DM architecture** on 2026-10-05, treating cost parity as a future optimization objective rather than an adoption gate. That decision does not establish production readiness or measured cost parity. The [design](README.md) and [test plan](test-plan.md) describe the intended system and broader evaluation; the normal game still uses the existing scribe pending hardening and integration.

## Deterministic verification

The final repository suite passed with four workers: **4,057 tests passed, 14 skipped**, across 231 files. Lint and TypeScript checks passed. The initial fully parallel run hit an existing React performance-test timeout; that test passed alone and the complete suite passed with bounded concurrency. An intermediate run also caught the intentionally changed private-conversation expectation while the corresponding test was being updated; the final tests retain private DM annotations and assert their exclusion from public surfaces.

New tests exercise streaming delimiter splits and malformed framing, causal event order, complete-exchange batching, feedback delivery after a successful durable DM response, ordinary-turn concurrency, dependent lifecycle drains, abandoned-worker fences, continuing context across reload, late resource/UI persistence, and recovery of completed exchanges after interrupted persistence/enqueue. They do not establish general exactly-once recovery for regenerated model tool batches, player-profile appends, or paid image requests.

## Repairs after the measured runs

The measured source stayed fixed during the paced run. Subsequent deterministic review added a targeted `search_campaign` freshness barrier, since that helper can read canonical entities just like `knowledge`. It also found that an accepted background resource update could yield during persistence, then publish an older value after a newer foreground write. The repair rechecks fields before publication, preserves independent keys, and persists the current resource state before acknowledging the background batch. Overlap tests exercise the actual disk-write await and a fresh-loader read. Asynchronous theme work receives additional revision guards. These repairs are not retroactively credited to the measured runs.

Both recorders now deep-clone data-only request and result snapshots and compute hashes before invoking the provider. Offline preparation and dedicated runner checks validate the revised harness; another live run is not claimed for these post-run fixes.

Seventeen engine integration tests now include delayed styling and location lookup conflicts, checking current canonical location fields, persisted UI, and callback output. A revision change after canonical location-update dispatch still needs a transactional storage precondition; the current guard cannot cancel an already-dispatched update. This remains a production-hardening item alongside the broader recovery limitations.

## Decision and remaining work

The architecture is selected: both schedules substantially reduced observed ordinary-turn latency, and the paced comparison retains that advantage after allowing baseline maintenance time to finish. The owner considers that benefit decisive and directs development to proceed on the assumption that cost can be tuned to parity. The measured prototype did **not** break even with Sol 6.1 in the maintenance role: full-workload estimates rose approximately 58–69%. Preserve that evidence while treating cost tuning as optimization work, not a reason to reconsider the architecture.

The next implementation priorities are a defined bootstrap feed, recovery-safe effects, private/public publication and authorship safeguards, and production lifecycle integration. Preserve ordinary-turn concurrency and the earned foreground prompt guidance while hardening those paths. A **Luna co-DM**, more selective context, and revised batching are possible optimization experiments; none is a prerequisite for the architecture decision, and no cost-parity result is claimed here.

These selected pilots do not establish production readiness. Shared summary/publication errors, bootstrap coverage, crash/replay limitations, disabled image work, and the small number of independently generated branches remain material. The default game behavior stays unchanged.
